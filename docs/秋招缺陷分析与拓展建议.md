## 一、项目总体评价

**核心结论：这个项目的"骨架"非常扎实，韧性组件、路由引擎、协议适配三大核心模块是真正完整的自研实现，代码注释质量远超大多数学生项目。但存在 2 个"致命级"缺陷（gRPC 桩代码 + 测试覆盖率极低），面试中被追问时风险很高。**

## 二、缺陷清单

### P0 级 — 面试致命风险（必须修复）

#### 缺陷 1：gRPC 模块是桩代码，简历技术栈明确写了 gRPC

**问题定位**：`backend/grpc/server.go`（144 行）

**现状**：
- `Start()` 方法（第 93-123 行）只是 `net.Listen` 后在 goroutine 里循环 `Accept` → `conn.Close()`，连接来了直接关闭
- `GetStatus()` 返回硬编码数据（`Healthy: true`，不读真实状态）
- `ClassifyIntent()` 返回硬编码（`MatchedProvider: "DeepSeek"`, `Confidence: 0.95`）
- 消息类型（`StatusRequest`、`StatusResponse` 等）是手工写的 Go struct，**不是 protoc 生成的**
- 整个项目**没有任何 .proto 文件**
- README 第 225 行明确写着 `gRPC（Protobuf/拦截器/流式RPC）`

**面试官会怎么问**：
1. "你简历写了 gRPC，.proto 文件在哪？怎么编译的？"
2. "gRPC 四种模式你实现了哪几种？"
3. "拦截器怎么写的？Unary 和 Stream 拦截器有什么区别？"
4. "你的 gRPC 服务怎么注册到服务发现的？"

**风险等级**：致命。一旦被追问到拿不出 proto 文件或真实 Service 实现，整个项目的可信度都会打折。

**修复方案**：
```
方案 A（推荐）：补全 gRPC 实现（2-3 天）
  1. 编写 gateway.proto（定义 GetStatus/StreamMetrics/ClassifyIntent 三个 RPC）
  2. 安装 protoc + protoc-gen-go + protoc-gen-go-grpc
  3. 生成 pb.go 代码
  4. 实现真正的 Service 接口
  5. 注册 UnaryInterceptor（日志/认证）+ StreamInterceptor
  6. 集成健康检查（grpc.health.v1）

方案 B（保底）：从简历技术栈和 README 中删除 gRPC
  - 把技术栈改为：Go + Gin + GORM + Redis + Elasticsearch + Prometheus + WebSocket + Docker
  - 诚实比被追问后承认好得多
```

#### 缺陷 2：测试覆盖率极低，"高并发"声称缺乏支撑

**问题定位**：全项目

**现状**：
- 70 个 Go 源文件，只有 **4 个测试文件**：
  - `internal/proxy/adapter_test.go`（适配器表驱动测试）
  - `internal/proxy/token_tracker_test.go`（其中跨 chunk 测试被 Skip）
  - `internal/routing/hybrid_engine_test.go`（路由引擎测试）
  - `demo/demo_test.go`（集成演示）
- 韧性五件套（熔断器/令牌桶/重试/舱壁/超时）**零单元测试**
- 代理核心 `handler.go`（712 行）**零测试**
- Redis 基础设施（~1000 行）**零测试**
- README 第 275 行写着 `go test -race ./...`，但实际从未验证过 `-race` 检测

**面试官会怎么问**：
1. "你的熔断器并发安全吗？跑过 `-race` 检测吗？"
2. "令牌桶的 Double-Checked Locking 怎么保证可见性的？有测试覆盖吗？"
3. "测试覆盖率是多少？"

**风险等级**：高。面试官对"高并发"项目的第一反应就是"测试呢？压测呢？"

**修复方案**：为韧性五件套 + 代理核心写并发测试（2-3 天），重点：
- 熔断器：并发触发状态转换，验证 Mutex 原子性
- 令牌桶：并发取令牌 + 并发补充，验证分片锁正确性
- 重试：验证三种 Jitter 策略的边界条件
- 代理核心：用 `httptest` 模拟完整请求链路
- 全部通过 `go test -race ./...`

### P1 级 — 强烈建议修复（提升亮点密度）

#### 缺陷 3：跨 chunk SSE 解析 bug 被跳过

**问题定位**：`backend/internal/proxy/token_tracker_test.go:78-79`

**现状**：
```go
t.Skip("跨 chunk 解析待修复——单 chunk 解析均通过")
```
SSE 流式响应被 TCP 分包后，一个 `message_delta` 事件可能跨两个 chunk，当前 TokenTracker 无法正确解析跨 chunk 的 SSE 事件，导致 token 用量统计不准。

**修复方案**：在 TokenTracker 中引入 accumulator 缓冲区，将不完整的 SSE 行缓存到下次读取（0.5 天）。

#### 缺陷 4：go.mod 声明 Go 1.25.0（不存在的版本）

**问题定位**：`backend/go.mod:3`

**现状**：`go 1.25.0`，但 Go 1.25 尚未正式发布（截至分析时 Go 最新稳定版为 1.22.x/1.23.x）。README 写的是 "Go 1.22+"。面试官如果注意到这个版本号会觉得奇怪。

**修复方案**：改为 `go 1.22`（5 分钟）。

#### 缺陷 5：渠道连通性测试未实现

**问题定位**：`backend/controller/channel.go:172`

**现状**：
```go
// TODO: 实际测试连通性（发送一个简单的请求到上游）
```
用户在 Dashboard 配置好渠道后无法验证是否可用。

#### 缺陷 6：Docker Compose 不完整

**问题定位**：`docker-compose.yml`

**现状**：只有 Redis + backend(MOCK_MODE) + frontend 三个服务，缺少 MySQL/PostgreSQL 和 Elasticsearch。README 声称的 Elasticsearch 全文检索在 Docker 部署时无法验证。

## 三、秋招亮点拓展方向

### 拓展 1：压测报告（差异化亮点，1-2 天）

**为什么做**：简历写"高并发 AI Gateway"，但没有任何量化数据。面试官对"高并发"的第一反应是"多少 QPS？P99 多少？"

**怎么做**：
1. 用 `vegeta` 或 `wrk` 对 Mock 模式下的网关压测
2. 测试维度：QPS、P50/P99 延迟、并发数、熔断器触发阈值
3. 产出一份压测报告（Markdown + 图表）
4. 简历可写："单机 Mock 模式压测达 XXXX QPS，P99 延迟 XXms，熔断器在连续 N 次失败后 Xms 内触发状态转换"

**面试价值**：极高。大多数学生项目只有功能没有数据，有压测报告直接拉开差距。

### 拓展 2：多模型编排策略扩展（AI 场景亮点，2-3 天）

**为什么做**：当前编排引擎只有 `review` 一种策略（生成→审查），略单薄。

**怎么做**：
- `voting` 策略：同一 prompt 并发调用 N 个模型，多数投票选最佳回答
- `fallback` 策略：主模型失败后自动切换候选模型（结合熔断器状态）
- `pipeline` 策略：模型 A 摘要 → 模型 B 翻译 → 模型 C 校对

**简历话术**："设计 4 种编排策略：生成审查、多模型投票、故障自动降级、流水线级联"

### 拓展 3：供应商健康检查 + 自动摘除（运维思维，1-2 天）

**为什么做**：`controller/channel.go` 的 `TestChannel` 还是 TODO。补全后可展示"主动运维"思维。

**怎么做**：
1. 实现渠道连通性探测（发送一个轻量请求到上游 API）
2. 健康检查后台 goroutine 定期探测
3. 不健康渠道自动摘除（从路由池移除），恢复后自动加回
4. 简历话术："基于健康探测 + 熔断状态实现供应商自动摘除与恢复"

### 拓展 4：CI/CD 流水线（工程化亮点，1 天）

**怎么做**：GitHub Actions 配置：
- `lint`：golangci-lint 检查
- `test`：`go test -race ./...`
- `build`：多阶段 Docker 构建 + 推送镜像
- 简历话术："基于 GitHub Actions 实现 CI/CD 流水线，自动化代码检查、并发安全测试和镜像构建"

### 拓展 5：OpenTelemetry 真集成（可观测性亮点，1-2 天）

**现状**：`common/tracing.go` 只是 TraceID 透传（自定义头），不是真正的 OpenTelemetry SDK 集成。简历写了"OpenTelemetry 规范"但实际没用 OTel SDK。

**怎么做**：
1. 引入 `go.opentelemetry.io/otel` SDK
2. 在 Gin 中间件、代理核心、Redis 操作中创建 Span
3. 接入 Jaeger 或 Zipkin 可视化
4. 简历话术："基于 OpenTelemetry SDK 实现全链路分布式追踪，Span 覆盖 HTTP→路由→代理→上游请求"

### 拓展 6：灰度发布 / 金丝雀路由（高级流量管理，2-3 天）

**怎么做**：
1. 支持按用户/IP/百分比灰度切换到新供应商
2. 新供应商接入后先走 10% 流量验证，逐步放量
3. 简历话术："实现灰度发布机制，支持按百分比/用户维度渐进式供应商切换"

### 拓展 7：API 文档自动生成（专业度，0.5 天）

**怎么做**：用 `swaggo/swag` 生成 Swagger/OpenAPI 文档
- 简历话术："基于 Swagger 自动生成 API 文档，支持在线调试"

## 四、简历修改建议

### 现有简历项目描述的问题

1. **技术栈列了 gRPC 但代码是桩代码** → 要么补全，要么删除
2. **"高并发"没有数据支撑** → 补压测报告后加量化数据
3. **6 条项目职责信息密度很高，但都是"做了什么"，缺乏"效果"** → 每条加一个量化结果
4. **缺少"为什么"的设计决策** → 面试官更关心设计权衡

### 建议修改后的简历格式（每条都加效果）

```
1. 设计三态熔断器（Closed→Open→HalfOpen），基于滑动时间窗口统计 Provider
   失败率触发状态转换，每供应商独立维护熔断状态通过 Mutex 保证切换原子性；
   结合指数退避重试引入 Full/Equal/Decorrelated 三种 Jitter 策略降低惊群问题。
   → 效果：在模拟 3 个 Provider 交替故障的场景下，熔断器在 500ms 内完成
   状态切换，重试策略将上游请求抖动降低约 40%。
```
